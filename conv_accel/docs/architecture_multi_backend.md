# Архитектура: единый C++/OpenCV проект с бэкендами OpenCL / CUDA / FPGA

Цель: одно приложение на C++/OpenCV, которое вызывает одну и ту же
деконволюцию через `OpenCL GPU`, `CUDA GPU` или `FPGA`, выбирая бэкенд
на старте. FPGA-бэкенд — плата YPCB-00338-1P1 (Kintex-7 XC7K480T,
PCIe x4 Gen2, DDR3).

## API

`host/include/deblur/deblur.h`:

```cpp
deblur::MotionParams p;      // dx, dy, dalpha, exposure, nsr, block, hop
auto eng = deblur::Engine::create(deblur::Backend::FPGA);
eng->process(src, dst, p);   // cv::Mat / cv::UMat
```

Бэкенды:

| Backend | Реализация |
|:--|:--|
| `CPU` | эталон на хосте (та же блочная схема, для проверки) |
| `OpenCL` | `cv::UMat`, `cv::dft`/`mulSpectrums` или свои ядра |
| `CUDA` | `cv::cuda::GpuMat`, `cv::cuda::dft` или свои ядра |
| `FPGA` | PCIe → AXI DMA → DDR3, блочный FFT-винер на плате |

`Backend::Auto` выбирает первый доступный (FPGA → CUDA → OpenCL → CPU).

## Что уже измерено по FPGA

### FFT-ядро: 24 бита, `unscaled`, `realtime`

| вариант | DSP | BRAM18 | LUT | FF | поток |
|:--|--:|--:|--:|--:|:--|
| `hls::fft` fp32, `nonrealtime` | 34 | 7 | 11 645 | 14 625 | 0.31 отсч./такт |
| `xfft` 16 бит, `realtime`, scaled | 12 | 4 | 2 511 | 4 530 | 1 отсч./такт |
| `xfft` 24 бита, `realtime`, `unscaled` | **18** | **4** | 2 927 | 5 339 | **1 отсч./такт** |

8 ядер 24-бит: **144 DSP (7.5 %), 32 BRAM18 (1.7 %)**.

Почему 24 бита: 16-битный промежуточный спектр (между строками и
столбцами) теряет мелкие бины — round-trip 22.7 дБ. 24-битный даёт
**70.8 дБ**, а винер — **52.2 дБ** против float-эталона (max|err| 7e-5).

Realtime включается приватной копией `hls_fft.h` с
`throttle_scheme=realtime` (генерируется в `build.tcl`); fixed-point API
`hls::fft<config>` с `ap_fixed<24,1>` работает как есть.

### Сколько ядер нужно

Стоимость блочного 2D-FFT на выходной пиксель:

```
2 прохода (строки + столбцы) × 2 (FFT + IFFT) × 4 (перекрытие 50%) = 16 отсчётов/пиксель
```

| режим | пикселей/с | отсчётов/с | ядер по 250 МГц |
|:--|--:|--:|--:|
| 1080p30 | 62.2 M | 0.99 G | **4** |
| 1080p60 | 124.4 M | 1.99 G | **8** |

8 ядер 24-бит: **144 DSP (7.5 %), 32 BRAM18 (1.7 %)**. Дёшево.

**Измеренная пропускная способность (важно).** В синтезе row-pass
каждое ядро даёт **878 тактов на 256-точечный FFT = 3.4 такта/отсчёт**,
а не 1. Обёртка `hls::fft` сливает pipeline между вызовами (на каждый
вызов — свой config/status). Загрузка/выгрузка при этом идут по
8 отсчётов/такт, т.е. память не узкое место.

Следствие: 8 ядер = **2.35 отсчёта/такт** → ~20 fps, не 60.

Варианты:
1. **Прямой `xfft` IP в BD** с непрерывным AXI-Stream и `tlast` каждые
   N отсчётов (без перезаписи config на кадр) — целевое 1 такт/отсчёт,
   тогда 8 ядер достаточно.
2. **~27 ядер** при текущей обёртке: 27 × 18 = 486 DSP (25 %),
   ~108 BRAM18 (5.6 %) — влезает, но управление 27 потоками сложнее.

### Где реальная стоимость — память

Текущий проект уже занимает **172.5 / 955 RAMB36 (18 %)**. Рабочий
блок — **256×256, hop 128**. При перекрытии 50 % стоимость на пиксель
не зависит от размера блока (16 отсчётов/пиксель), а 256 даёт **лучший
PSNR**, чем 512:

| D | размыто | B512 / h256 | B256 / h128 |
|--:|--:|--:|--:|
| 0.2 | 21.61 | 28.21 | **30.01** |
| 0.5 | 19.31 | 23.94 | **24.88** |

Буфер 256×256 комплексных Q17.15 (`unscaled` FFT, 32 бита) = 512 КБ =
~114 RAMB36 (12 %). Два буфера = **24 %**, плюс 8 FFT-ядер и таблицы —
итого **~37 %** вместе с текущим проектом. Запас большой.

Почему `unscaled`, а не 16-битный BFP: у обратного FFT промежуточный
рост `N²` уводит изображение ниже LSB 16 бит (проверено в csim —
картинка разрушается). `unscaled` даёт 16-битный вход и 25-битный выход
(Q17.15); изображение сохраняется, а блок-нормализация спектра перед
обратным FFT использует все 16 бит.

Буферы раскладываются по плиткам 8×8:

```
buf[c/8][r/8][c%8][r%8]
#pragma HLS array_partition variable=buf complete dim=3
#pragma HLS array_partition variable=buf complete dim=4
```

Тогда и запись транспонирования (8 строк в один столбец), и чтение
8 столбцов идут по 8 разным банкам — 8 отсчётов/такт без конфликтов.

### PSF: отрезок вместо дуги

Точная локальная PSF — дуга. Проверка на `D=0.5` (тот же стенд):

| PSF на блок | всё | центр | 400–700 | углы |
|:--|--:|--:|--:|--:|
| точная дуга | 23.94 | 27.32 | 25.02 | 21.01 |
| отрезок (`L`, `θ` в центре блока) | 24.02 | 27.29 | 25.07 | 21.12 |
| **аналитическая sinc-OTF** | **24.05** | 27.52 | 25.08 | 21.14 |

То есть достаточно двух чисел на блок:

```
s = T + (R(Φ) − I)(r0),   L = |s|,   θ = atan2(sy, sx)
a = (L/B)(kx cosθ + ky sinθ)
H = exp(−iπa)·sinc(πa)
G = conj(H)/(|H|² + nsr)
```

`G` нельзя считать через `double sin/cos`: синтез даёт **3327 DSP
(173 %)**. Нужна LUT: хост считает 8–16k значений `G(a)` (Q1.15) для
текущих `nsr, gs` и загружает в BRAM; ядро делает
`a = (L/B)(kx cosθ + ky sinθ)` → индекс → `G`.

## Поток данных FPGA

```
host: cv::Mat
  └─ AXI DMA → DDR3 (входной кадр)
       └─ kernel (m_axi):
            для каждого блока 256×256 с перекрытием:
              load → 2D FFT (строки → транспонирование → столбцы)
              → G = conj(H)/(|H|²+nsr)   (PSF в центре блока)
              → 2D IFFT → окно/накопление
            → DDR3 (выходной кадр)
  └─ AXI DMA → cv::Mat
```

Параметры `(dx, dy, dalpha, exposure, nsr)` — в AXI-Lite регистрах.
PSF на блок — отрезок `(L, θ)` из траектории; `G` — аналитический
`sinc`-OTF (см. выше), без буфера под PSF.

### Карта user BAR (64 КБ)

| offset | размер | устройство |
|:--|:--|:--|
| `0x0000` | 4 КБ | `axi_dma_0` (платформенный DMA) |
| `0x1000` | 4 КБ | `conv2d_0` |
| `0x2000` | 4 КБ | `axi_dma_1` (deblur DMA) |
| `0x4000` | 8 КБ | `wiener_0`, `params[3][256]` по `+0x1000` |

Адреса заданы явно в `scripts/fix_bd_addresses.tcl`. Голый
`assign_bd_address` (как в `add_wiener_bd.tcl`) ставил `axi_dma_1` на
`0x41E00000`, а `wiener_0` на `0x00010000` — обе точки вне 64 КБ BAR,
поэтому регистры читались как `0xFFFFFFFF`. Тем же скриптом
`axi_dma_1/Data_MM2S|S2MM` получают сегмент DDR3 c0 (`0x0`, 2 ГБ):
`assign_bd_address` его не создавал, и мастер DMA1 не был подключён к
памяти.

### FIFO на выходах xfft (обязательно)

Обёртка `xfft` (pipelined streaming I/O) **не имеет**
`m_axis_data_tready`: внутри ядра он притянут к `1`, данные выходят
независимо от готовности потребителя. Ядро читает 8 потоков
`fwd_out`/`inv_out` синхронно и поднимает все `TREADY` только когда
все 8 отсчётов на месте, поэтому один опоздавший отсчёт «съедает»
остальные семь — проход заканчивается недобором, и ядро ждёт
навсегда (в железе: DMA уже отдал весь вход, `ap_done` не приходит,
в DDR не записан ни один пиксель).

Лечение — `axis_data_fifo` (глубина 512, 80 бит) между каждым
`fft_*_i/M_AXIS_DATA` и `wiener_0/fwd_out_i|inv_out_i`
(`scripts/add_fft_fifos.tcl`). FIFO честно держит `TREADY`, и
рассинхронизация ядер поглощается.

### Про «старый образ» во флеше

Платформенный и новый образы неразличимы по `0x0`/`0x1000`:
`axi_dma_0` в обоих отдаёт `0x00010002`, `conv2d_0` — `0x00000004`
(`ap_idle`). «Старый образ» в диагностике был ошибкой: адреса
`0x2000/0x4000` не отвечали и в новом образе, потому что декод был
собран вне BAR. После правки адресов `scripts/bar_probe.py` сразу
показывает `dma1`/`wiener`.

## Этапы

1. **csim 2D FFT 64×64** — сделан: max|err| 4e-5, структура
   строки → транспонирование → столбцы верна.
2. **csim блока 128×128, 8 ядер, float** — сделан: **131.3 дБ** против
   CPU. Структура FFT → G → IFFT и плиточное транспонирование верны.
3. **csim 128×128, 8 ядер, 24 бита `unscaled`** — сделан: round-trip
   **70.8 дБ**, винер **52.2 дБ** против float.
4. **LUT для `G`** — сделан: **51.3 дБ**, DSP в синтезе 3327 → 672.
5. **Синтез 256×256, 8 ядер** — сделан: ядра параллельны (144 DSP,
   Fmax 324 МГц), но **3.4 такта/отсчёт** на ядро → ~20 fps.
6. **Прямой `xfft` IP** — подтверждён **1 такт/отсчёт** (512 отсчётов
   за 512 тактов, кадры вплотную). Обёртка была виновата.
7. **HLS-ядро с 32 AXI-Stream портами** (8 fwd + 8 inv) — синтез:
   BRAM 30 %, DSP 20 %, Fmax 255 МГц. Латентность блока 156k тактов,
   из них FFT-конвейер 26k (~14 мс/кадр), остальное — поток пикселей
   по 1/такту.
8. **Strip/frame контроллер (Y-only)**: чтение кадра один раз в
   strip-буфер, блочный конвейер — убрать 4-кратное чтение и
   перекрыть I/O с FFT. Цель 60 fps.
9. **BD**: 16 xfft IP + ядро + AXI DMA; хост `deblur::Engine`.
10. **OpenCL/CUDA бэкенды** за тем же `deblur::Engine`.

## Статус на 2026-11-20

Что проверено на железе (образ 178.57 МГц, JTAG):

- user BAR: `dma1` (`0x2000`) и `wiener_0` (`0x4000`) отвечают,
  `width/height/params/dbg` пишутся и читаются;
- AXI DMA #1 отдаёт весь кадр (TX `IOC|Idle`), т.е. ядро вычитывает
  вход полностью;
- ядро стартует (`CTRL=1`, `ap_idle=0`), но **не доходит до выдачи**:
  в DDR не записан ни один пиксель, `RX DMA` не завершается.

Где именно стоит ядро (по состоянию потоков через system_ila при
зависании):

| поток | TVALID | TREADY |
|:--|:--|:--|
| `din` | 0 (или 1 при лишних отсчётах) | 0/1 |
| `fwd_in_0` (ядро → xfft) | 0 | 1 |
| `fft_fwd_0/m_axis` | 0 | — |
| `inv_in_0` / `inv_fifo_0` | 0 | 1 |
| `dout` | 0 | 1 |

То есть к моменту зависания все потоки простаивают: отправка в xfft
либо уже закончилась, либо ещё не начиналась, а xfft ничего не выдаёт.
C/RTL-моделирование ядра (stub-FFT, соблюдающий TREADY) проходит
целиком (`513k` тактов, 65536 отсчётов на выходе), поэтому логика
блока в RTL корректна; расхождение — во взаимодействии с xfft в BD.

Что уже исключено:

- адресация AXI-Lite (исправлена, см. выше);
- память DMA1 (сегменты DDR3 c0 назначены);
- нехватка входных отсчётов (лишние 16/4096 отсчётов не помогают);
- параметры (переведены на Q1.15 `ap_int<32>`, float-IP удалён);
- тактирование/сброс домена ядра (WNS `+0.13`, WHS `+0.05`).

Следующий шаг отладки — снять `ap_CS_fsm` ядра (netlist debug / ILA
на внутренней сети) либо прогнать вариант с петлёй
`fwd_in → fwd_out` вместо xfft. Это разделит «логику региона
dataflow» и «поведение xfft в BD».

### Регистры ядра (актуально)

| offset | что |
|:--|:--|
| `0x0000` | CTRL |
| `0x0010` | width |
| `0x0018` | height |
| `0x0020` | `out_scale` — общий коэффициент выходной яркости (см. ниже) |
| `0x0040..0x7F` | `dbg[16]` — отладочные метки (пишет ядро) |
| `0x1000..0x1BFF` | `params[3][256]`, Q1.15 в младших 16 битах слова |

Хост (`deblur_fpga.cpp`) пакует `(L/N, cosθ, sinθ)` в Q1.15 и пишет
`out_scale` (`DEBLUR_FPGA_SCALE`, по умолчанию 1 340 000).

## Обновление 2026-11-21: ядро переведено на внутренний `hls::fft` (устарело, см. 2026-11-22)

Внешние 16 × `xfft` + 16 × `axis_data_fifo` из BD убраны: они принимали
данные, но **не выдавали результат** в железе (в симуляции та же
конфигурация работает). Ядро `wiener_stream` теперь содержит 8
параллельных потоковых `hls::fft` (`row_par_test`-стиль), собирается и
закрывает тайминг (WNS `+0.011`).

Ключевой эксперимент: если замкнуть потоки ядра на себя
(`fwd_in → fifo → fwd_out`, скрипт `scripts/bd_loopback.tcl`), ядро
проходит все три прохода (`dbg = 30,40,50,60,70,80`) — dataflow и
блочная арифметика в железе корректны. С xfft (и внешним, и через
`hls::fft`) блок стоит на первом проходе: ядро xfft не отдаёт данные.

Что уже проверено/исключено для xfft:

- конфигурация 256 точек, 24 бита, `unscaled`, `realtime`, natural order;
- постоянный `config_tvalid`, одиночный импульс 32 такта, отсутствие
  конфигурации (в симуляции все три работают);
- TLAST каждые 256 отсчётов, `m_axis_data_tready` (в упакованном ядре
  пришлось добавить порт — `scripts/patch_hls_fft_core.py`);
- тактирование/сброс домена (WNS домена ядра `+0.010`).

Следующий шаг — отдельный минимальный тест xfft в железе (известный
вход + ILA на выходе) либо замена FFT на заведомо рабочий вариант
(например, собственная radix-2 в HLS или `scaled`-режим).

Флеш по-прежнему содержит старый образ; холодный ребут не делался,
текущие образы загружались только по JTAG.

## 2026-11-22: внешние xfft заработали, FPGA-бэкенд сдаёт кадр

Итог: `deblur_demo --backend fpga` обрабатывает 1920×1080 полностью на
плате (Y-винер, 256×256 блок, шаг 128), хост передаёт только кадр и
параметры движения. Проверено по JTAG, холодного ребута не было.

Что было не так и что исправлено:

1. **`inv_rows` зависал.** `row_pass`/`col_pass` имели `#pragma HLS
   dataflow`, а `inv_rows` — нет; Outline-процесс приёма не стартовал.
   Добавление прагмы не помогало (HLS 200-656: auto-rewind процессы в
   dataflow могут дедлочиться на старте — это плавающий эффект).
   **Решение:** все три прохода переписаны последовательными циклами без
   dataflow; кадры (по 256 отсчётов на 8 линиях) ведутся конвейером
   send(k) / recv(k−D). Внешние FIFO развязывают latency xfft.
2. **Выход не писался в DDR.** У AXIS-мастера `dout` не были выставлены
   `TKEEP/TSTRB` (0 → S2MM игнорирует beat). Теперь `keep = strb = -1`.
3. **Вход терял динамический диапазон.** `sample_t(yv−128)/256`
   сатурировался к ±1 (Q1.23), т.е. делился ещё на 128. Заменено на
   `ap_fixed<16,8>(yv−128) >> 8`.
4. **Хвост кадра 1080p затирал строки.** Главный цикл выдаёт 0…1023,
   хвостовой проход выдавал все 128 строк (952…1079) → перекрытие 72
   строки и ошибка S2MM. Теперь хвост выдаёт только непокрытые строки
   (`j0 = covered − last_vy`).
5. **Фаза фильтра была сопряжённой относительно CPU.** `cv::dft` в
   OpenCV и xfft используют разные соглашения ДПФ, поэтому выход FPGA
   был сдвинут на вектор движения (проверено: dx=20 → сдвиг +20 px,
   корреляция 0.9997 после сдвига). В `gbin_lut` инвертирован знак
   мнимой части (`g_lut_im`); после этого FPGA совпадает с CPU.
6. **Масштаб выхода.** Фиксированная точка даёт общий коэффициент
   ~1.34e6; он вынесен в регистр `out_scale` (0x20), чтобы калибровать
   без пересборки. Калибровка по CPU: наклон 1.005 при `out_scale =
   1 340 000`.

Результаты (JTAG, образ 178.57 МГц):

| тест | PSNR FPGA vs CPU | corr |
|:--|--:|--:|
| 256×256, dx=20 / dy=20 / 14,14 | 45.8…45.9 дБ | 0.9997 |
| 1080p, dx=9 (blur 9 px) | 42.8 дБ | 0.9999 |
| 1080p, da=0.02 (вращение) | 32.4 дБ | 0.990 |
| 1080p, нулевое движение | 47.3 дБ (256×256 low-contrast) | — |

Скорость: 1080p — **0.30 с** на кадр через `deblur_demo` (включая
XDMA-передачу 8 МБ в DDR и 8 МБ обратно); ядро на 1920×1024 в
регистровом тесте — 0.34 с. Отладочные счётчики `dbg[10..14]` из
горячего пути убраны.

Ограничения/дальше: точность промежуточного Q1.23 и LUT дают ~46 дБ
против float-CPU; для 60 fps нужен более быстрый strip-контроллер
(сейчас ~3.5 мс на блок) и/или конвейер блоков. Параметры движения —
Q1.15, `params[3][256]` (до 256 блоков; для 4K нужно расширение).
