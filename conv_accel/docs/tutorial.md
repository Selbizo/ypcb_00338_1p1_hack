# Учебник: как сделан проект ускорения деблюра на FPGA

Это методичка «от нуля до рабочего кадра» по проекту `conv_accel`:
плата YPCB-00338-1P1 (Kintex-7 XC7K480T), PCIe, DDR3, BPI-флеш,
HLS-ядро на 16 × xfft и хост на C++/OpenCV.

Читать можно последовательно, но если нужен быстрый вход — разделы
3 (методика), 8 (отладка) и 11 (чек-листы) дают больше всего практики.

---

## 1. Задача и общая картина

### 1.1 Что делает проект

Проект убирает **смаз от движения** (motion deblur) на видео/изображении.
Пользователь даёт кадр и параметры движения (`dx`, `dy`, `dalpha`,
`exposure`, `nsr`), получает восстановленный кадр.

Одна и та же процедура реализована четырьмя способами за общим API:

```cpp
deblur::MotionParams p;
auto eng = deblur::Engine::create(deblur::Backend::FPGA);
eng->process(src, dst, p);          // cv::Mat -> cv::Mat
```

| Backend | Где считается |
|:--|:--|
| `CPU` | хост, OpenCV, float — эталон |
| `OpenCL` | GPU через `cv::UMat` / OpenCV T-API |
| `CUDA` | GPU через `cv::cuda::GpuMat` |
| `FPGA` | плата: PCIe → DDR3 → AXI DMA → 16 × xfft + ядро → обратно |

### 1.2 Зачем FPGA и зачем стенд

FPGA здесь не «потому что модно», а потому что потоковый FFT-конвейер
можно сделать с детерминированной задержкой и без участия CPU. Стенд
`deblur_bench` нужен, чтобы сравнивать реализации на одной задаче:
время, fps и PSNR относительно CPU. Подробности — `docs/benchmark.md`.

### 1.3 Архитектура в одном рисунке

```
хост (C++ / OpenCV)                          плата
┌──────────────────────────┐   PCIe x4   ┌─────────────────────────────┐
│ кадр Y (32-бит слова)    │ ──────────► │ DDR3 (XDMA)                 │
│ параметры блоков Q1.15   │             │   │                         │
│                          │             │   ▼ AXI DMA (MM2S)          │
│                          │             │ ядро wiener_stream          │
│                          │             │   ├─ 8 × xfft forward       │
│                          │             │   ├─ 8 × xfft inverse       │
│                          │             │   └─ strip/outst, LUT       │
│                          │ ◄────────── │   │                         │
│                          │             │   ▼ AXI DMA (S2MM) → DDR3   │
└──────────────────────────┘             └─────────────────────────────┘
```

Важно: **два разных DMA**. XDMA гоняет данные хост↔DDR3, AXI DMA —
DDR3↔ядро. Это разные движки, у них разные регистры и разные грабли.

## 2. Железо: что нужно знать до первой сборки

### 2.1 Плата

| | |
|:--|:--|
| ПЛИС | Kintex-7 XC7K480T-FFG1156-2 |
| PCIe | x8 Gen2 умеет, слот даёт x4 Gen3 → тренируется x4 Gen2 |
| DDR3 | 2 канала, MIG с ECC (72 бит), AXI 512 бит |
| Флеш | Micron MT28GU512AAA, 512 Мбит, x16, **BPI, синхронный** |
| Питание | только слот PCIe, ~26 Вт |

Измеренный линк: ~1.5 ГБ/с в каждую сторону. Это важно для оценки:
кадр 1080p (8 МБ) в обе стороны — ~11 мс, и это **пол** для любого
FPGA-ускорения при такой схеме.

### 2.2 Карта адресов (user BAR, 64 КБ)

| offset | что |
|--:|:--|
| `0x0000` | `axi_dma_0` (платформенный/старый) |
| `0x1000` | `conv2d_0` |
| `0x2000` | `axi_dma_1` (деблюр) |
| `0x4000` | `wiener_0`, окно 8 КБ |

Регистры ядра:

| offset | что |
|--:|:--|
| `0x00` | CTRL (`ap_start`, `ap_done`, `ap_idle`) |
| `0x10` | width |
| `0x18` | height |
| `0x20` | `out_scale` — калибровка яркости |
| `0x40..0x7F` | `dbg[16]` — метки ядра |
| `0x1000..0x1BFF` | `params[3][256]`, Q1.15 |

DDR-адреса в хосте: вход `0x1000_0000`, выход `0x2000_0000`.

### 2.3 Тактовые домены

- PCIe user clock — 250 МГц (внутри XDMA);
- AXI-Lite/периферия — 100 МГц;
- **домен ядра — 178.57 МГц** (MMCM от 50 МГц `SYS_CLK`).

Между доменами стоят `axis_clock_converter` (`din_cc`, `dout_cc`) и
`lite_cc`. HLS-ядро живёт в домене 178.57 МГц; xfft — там же.

### 2.4 Сбросы

`proc_sys_reset` (`rst_215`, `rst_clk_wiz_1_100M`, MIG) формируют
`peripheral_aresetn`. Им сбрасываются FFT, FIFO, ILA и `ap_rst_n` ядра.
**Отдельного сброса FFT между запусками нет** — это важно (см. 8.2,
«залипшее состояние»).

## 3. Методика: как вообще строить такой проект

### 3.1 Этапы, которые прошёл проект

1. **Платформа**: PCIe, XDMA, DDR3, флеш, драйвер, JTAG.
2. **Малые ядра**: `passthrough`, `conv2d` — проверка тракта HLS → BD →
   DMA → память.
3. **Алгоритм на хосте**: CPU-эталон на float.
4. **Блочное ядро в C-симуляции**: FFT → G → IFFT, сравнение с float.
5. **Потоковое ядро**: внешние xfft, strip-контроллер.
6. **Интеграция**: host + self-test + полный кадр.
7. **Отладка стыков**: ILA, пробы FSM, регистровые метки.
8. **Ускорение**: профиль, II, банки памяти, хвост кадра.
9. **Стенд сравнения** и документация.

### 3.2 Главное правило: проверяй каждый стык отдельно

Типичная ошибка новичка — собрать всё сразу и искать «почему не
работает». Правильный путь:

```
float CPU  →  C-sim блока  →  loopback (без FFT)  →  один xfft  →  все 16  →  кадр
```

На каждом шаге должен быть **свой критерий**: число, картинка, PSNR,
осциллограмма ILA. Если шаг не проверен, следующий не начинают.

### 3.3 Воспроизводимость

- Генерируемые артефакты (`hw/accel.runs`, `hw/accel.gen`, `hw/ip_repo`,
  `hls/**/solution*`) — в `.gitignore`.
- В git — только исходники: HLS C++, скрипты, BD (`top.bd`), constraints,
  host, docs.
- Скрипты сборки и прошивки — в `scripts/`, команды в README.
- Каждый рабочий этап — отдельный коммит с цифрами в сообщении.

## 4. Алгоритм: что именно считается

### 4.1 Модель движения

Смаз описывается вектором смещения за выдержку:

```
T = exposure * (dx, dy)
Phi = exposure * dalpha
```

Для точки `p` относительно центра кадра смещение:

```
sx = Tx + (cos(Phi)-1)*rx - sin(Phi)*ry
sy = Ty + sin(Phi)*rx + (cos(Phi)-1)*ry
```

Длина `L = hypot(sx, sy)`, угол `theta = atan2(sy, sx)`. Внутри блока
движение считается постоянным (берётся в центре валидной плитки).

`dx`, `dy`, `dalpha` — это движение **за интервал между кадрами**, его
даёт `estimateAffine2D`. Реальная выдержка обычно короче этого интервала:
`D = t_выдержки / t_кадра`. Если принять `D = 1`, длина смаза завышается
в `1/D` раз (например, при выдержке 1/1000 с и 30 fps — в 33 раза).
В `deblur_video` поэтому задают `--shutter S` (секунды),
`--shutter-angle A` (градусы) или `--exposure D`; для `--shutter` D
считается по фактическому интервалу между кадрами, включая VFR.

### 4.2 Блочный винер

Кадр (канал Y) режется на блоки 256×256 с шагом 128. На выход идёт
центральная часть 128×128 — перекрытие 50 % убирает краевые эффекты.

Для блока:

1. 2D FFT (строками и столбцами).
2. Умножение на винеровский фильтр:

```
a  = (L/N) * (sx*cos(theta) + sy*sin(theta))    // нормированная частота
sc = sinc(pi*a)                                  // OTF равномерного смаза
G  = sc * exp(i*pi*a) / (sc*sc + nsr)
```

3. Обратный 2D FFT.
4. Центральные 128×128 пишутся в выход.

CPU-эталон делает это через `cv::dft`/`cv::mulSpectrums` во float.

### 4.3 Почему только Y

Глаз гораздо чувствительнее к яркости, чем к цвету. Деблюр только Y
даёт почти весь визуальный эффект при вдвое меньшем объёме работы.
Хрома берётся из исходного кадра.

### 4.4 Фиксированная точка и Q-форматы

В HLS нельзя «просто float» (дорого по DSP/латентности). Используется:

- вход/промежуточные `ap_fixed<24,1>` — 1 знаковый бит, 23 дробных
  (Q1.23), диапазон `[-1, 1)`;
- параметры `Q1.15` (`ap_fixed<16,1>`), хост пакует `L/N`, `cos`, `sin`;
- широкий выход FFT `ap_fixed<40,17>` (Q17.23), потому что 256-точечный
  FFT даёт рост до 8 бит.

**Тонкость №1.** `ap_fixed<24,1>` насыщается на ±1. Если написать
`sample_t(y - 128) / 256`, то `sample_t(y-128)` сначала насытится к ±1,
и только потом разделится на 256 — динамический диапазон будет потерян.
Правильно:

```cpp
ap_fixed<16,8> d = yv - 128;      // целое в Q8.8
sample_t s = sample_t(d >> 8);    // (yv-128)/256 без насыщения
```

**Тонкость №2.** Общий коэффициент тракта (из-за сдвигов и LUT) —
не 1, а ~1.34e6. Он вынесен в регистр `out_scale` (0x20), чтобы
калибровать без пересборки. Калибровка: подать изображение, сравнить
наклон FPGA-выхода к CPU; при `out_scale = 1 340 000` наклон ≈ 1.005.

### 4.5 LUT вместо sinc на лету

Считать `sinc` и `exp` на каждом отсчёте дорого. Фильтр `G(a)` табулирован:
`g_lut_re[8192]`, `g_lut_im[8192]` (Q1.15), аргумент `a ∈ [-96, 96]`,
шаг ~0.023. В ядре — линейная интерполяция.

**Тонкость №3.** LUT хранит `gs * G`, где `gs = 0.05`, чтобы значения
влезли в Q1.15 (пик `G` ~5). Поэтому итоговый масштаб включает `1/gs`.

## 5. Ядро на HLS

Файл: `hls/kernels/wiener_stream/wiener_stream.cpp`.

### 5.1 Интерфейсы

```cpp
void wiener_stream(
    hls::stream<axis_in_t>  fwd_in[8],   // к 8 forward xfft
    hls::stream<axis_out_t> fwd_out[8],  // от 8 forward xfft
    hls::stream<axis_in_t>  inv_in[8],   // к 8 inverse xfft
    hls::stream<axis_out_t> inv_out[8],  // от 8 inverse xfft
    hls::stream<axis_frame_t> &din,      // кадр из AXI DMA
    hls::stream<axis_frame_t> &dout,     // кадр в AXI DMA
    int width, int height,
    ap_int<32> params[3][256],
    int out_scale, int dbg[16]);
```

`axis_in_t = ap_axis<48>` (24+24 бита), `axis_out_t = ap_axis<80>`
(40+40), `axis_frame_t = ap_axis<32>` (яркость в младшем байте).

### 5.2 Кадр и «8 линий»

256-точечный FFT обрабатывает один кадр за 256 тактов. 8 ядер работают
параллельно, поэтому блок 256×256 обрабатывается «кадрами по 8 строк»:
одна итерация = 8 строк × 256 столбцов, по одному отсчёту на линию.

Проходы:

- **row_pass**: для каждой группы из 8 строк — forward FFT по строке;
  результат транспонируется в `B`.
- **col_pass**: forward FFT по столбцу (читая `B`), умножение на `G`,
  inverse FFT; результат транспонируется обратно в `A`.
- **inv_rows**: inverse FFT по строкам; валидные 128 столбцов пишутся
  в `outst` с масштабом.

### 5.3 Почему проходы последовательные, а не dataflow

Первая версия использовала `#pragma HLS dataflow` (send и recv —
отдельные процессы). В железе это дало плавающий дедлок: процессы с
auto-rewind pipeline не стартовали (HLS 200-656), ядро стояло на
первом проходе.

**Решение:** убрать dataflow; сделать один последовательный цикл на
проход, который чередует кадры:

```
send frame k  →  recv frame k-D
```

Это создаёт конвейер по кадрам без dataflow-процессов и без дедлоков.
`D` подбирается так, чтобы FIFO успевал.

**Тонкость №4.** Попытка чередовать send/recv **на уровне отсчёта**
(быстрее в 2 раза, II=1) в железе портит кадры: realtime-throttle xfft
не любит пауз внутри кадра, а HLS-конвейер к тому же по-разному
задерживает `tdata` и `tlast`. Мы вернулись к покадровой схеме.

### 5.4 Упаковка AXIS: TLAST, TKEEP, TSTRB

- `TLAST` обязателен: один импульс на 256 отсчётов (конец FFT-кадра).
- `TKEEP/TSTRB` у 32-битного выхода в AXI DMA должны быть все единицы.
  Если их не выставить, S2MM молча не принимает beat — DMA не
  завершается, в DDR ничего нет. У нас это был один из главных багов:

```cpp
axis_frame_t o;
o.data = (ap_uint<32>)outst[j][c];
o.keep = -1;     // все байты валидны
o.strb = -1;
o.last = ...;
```

### 5.5 Масштабы и сдвиги

Цепочка (упрощённо):

```
A = (y-128)/256
row FFT       → сдвиг >>8 (компенсация роста N)
col FFT       → сдвиг >>8, умножение на G
inverse col   → сдвиг >>4
inverse row   → сдвиг >>4
out_scale     → в яркость
```

Сдвиги подобраны так, чтобы промежуточные значения влезали в Q1.23.
Итоговый коэффициент — константа тракта; его и калибрует `out_scale`.

### 5.6 II и отчёт HLS

После `csynth_design` смотри не только «синтезировалось», а:

- `Pipelining result: Final II = ...` для каждого цикла;
- latency (такты) и trip count;
- «Unable to schedule load ... limited memory ports» — это про банки.

Пример из проекта: загрузка блока из strip была II=4 (32774 такта),
потому что 8 строк читались из одного банка. После раскладки
`strip[32][8][W_MAX]` с `complete dim=2` стало **II=1 (8198 тактов)**.

## 6. Vivado Block Design

### 6.1 Состав

- `xdma_0` — PCIe endpoint (BAR user + H2C/C2H);
- `axi_dma_0/1` — DDR↔поток (деблюр использует `axi_dma_1`);
- `mig_7series_0` — DDR3;
- `microblaze_0` + `axi_emc_0` — служебный процессор/флеш;
- `clk_wiz_1`, `proc_sys_reset`;
- 16 × `xfft` (8 forward + 8 inverse), 16 × `axis_data_fifo`;
- `wiener_0` — HLS-ядро;
- `dbg_ila` — system_ila на 6 слотов;
- `axi_smc`, `axi_gpio`, IIC и т.д.

### 6.2 Клоки и конвертеры

Каждый домен пересекается через `axis_clock_converter`; AXI-Lite —
через `lite_cc`. Никогда не соединяйте потоки разных частот напрямую.

### 6.3 FIFO на выходах xfft

Глубина подбирается под «межкадровое расстояние» проходов. В финале:
fwd 2048, inv 2048. Слишком маленькая → FFT стопорится и send не может
идти; слишком большая → лишний BRAM.

### 6.4 ILA

`dbg_ila` (system_ila, 6 слотов, глубина 8192) удобна для быстрого
взгляда на потоки. **Тонкость:** её capture mode — ALWAYS, триггер
игнорируется; снимать надо `run_hw_ila -trigger_now` в нужный момент.
Для отложенных событий лучше netlist-ILA (см. 8.4).

### 6.5 Address Editor

После добавления IP обязательно:

- назначить адреса AXI-Lite (у нас `dma1=0x2000`, `wiener=0x4000`);
- проверить, что декодер попадает в 64 КБ user BAR;
- задать сегменты DDR3 для DMA (`0x1000_0000`, `0x2000_0000`).

Симптом ошибки: `bar_probe` не видит устройство, хотя в BD оно есть.

## 7. Хост

### 7.1 XDMA

Драйвер создаёт `/dev/xdma0_h2c_0`, `c2h_0`, `user`.
Смещение в `pread/pwrite` — это **AXI-адрес** (см. `docs/platform.md`).

```cpp
xdma_.write(0x10000000, in.data(), bytes);   // кадр в DDR3
xdma_.read (0x20000000, ob.data(), bytes);   // результат из DDR3
```

### 7.2 AXI DMA (simple mode)

Регистры (смещение от `0x2000`):

| MM2S | S2MM |
|--:|--:|
| `0x00` CR | `0x30` CR |
| `0x04` SR | `0x34` SR |
| `0x18` SRC | `0x48` DST |
| `0x28` LEN | `0x58` LEN |

Порядок: reset → clear status → src/dst → length → start; ждать IOC в
обоих SR. Длина — в **байтах**.

### 7.3 Параметры блоков

Хост считает для каждого блока `(L, theta)` по модели движения и
пакует:

```cpp
params[0*256 + idx] = q15(L / 256.0f);
params[1*256 + idx] = q15(cos(theta));
params[2*256 + idx] = q15(sin(theta));
```

Порядок блоков — тот же, что в ядре: `for vy` → `for vx`, затем
хвостовой блок.

### 7.4 Сборка кадра

1. BGR → YUV, взять Y.
2. Y → 32-битные слова (яркость в младшем байте), записать в DDR.
3. Запустить ядро, затем AXI DMA.
4. Дождаться `ap_done` и IOC.
5. Прочитать выход, собрать Y + исходную хрому → BGR.

### 7.5 Профилирование и стенд

`DEBLUR_FPGA_PROFILE=1` печатает:

```
fpga profile: write 8.2 ms, kernel 77.9 ms, poll 0.0 ms, read 5.4 ms
```

`deblur_bench` меряет медиану, fps и PSNR к CPU (см. `docs/benchmark.md`).

## 8. Отладка: главная часть

### 8.1 Иерархия проверок

Всегда снизу вверх:

1. **PCIe/XDMA**: `lspci`, `/dev/xdma0_*`, `dma_pattern`.
2. **User BAR**: `bar_probe.py` видит `dma1`/`wiener`.
3. **AXI DMA**: записать/прочитать DDR через DMA без ядра.
4. **Ядро, регистры**: width/height/params читаются.
5. **Потоки**: ILA на `din`/`dout`, потом на fwd/inv.
6. **Один FFT**: счётчик → xfft → ILA (минимальный тест).
7. **Loopback**: `fwd_in → fifo → fwd_out` (ядро без FFT).
8. **Полный кадр**: сравнение с CPU.

### 8.2 Таблица «симптом → причина»

| Симптом | Что проверить |
|:--|:--|
| Ядро не стартует, `dbg` нули | `ap_start`, `ap_rst_n`, старт dataflow-процессов |
| Ядро стоит на проходе (state21/25) | xfft не отдаёт данные: tready/tvalid, TLAST, FIFO |
| Выход весь 128 | нет AC: вход 0/сатурация, `G=0`, нет данных из FFT |
| Выход сдвинут на вектор движения | сопряжение фазы: `cv::dft` и xfft используют разные знаки ДПФ |
| «Размытый»/низкоконтрастный выход | совмещённые send/recv ломают кадры xfft |
| Мусор в первых строках/блоках | незачищенное состояние FIFO между запусками |
| DMA timeout (TX) | ядро прочитало меньше слов, чем длина DMA; `TKEEP=0` |
| DMA timeout (RX) | ядро не выдало все строки; TLAST/эмиссия |
| PSNR 27 дБ на 1080p, 44 на 1024 | хвост/перекрытие не совпадает с CPU |
| `End of startup LOW` при JTAG | битстрим собран с `STARTUPCLK=Cclk` |
| После прошивки нет PCIe | нужен холодный старт или `reprobe.sh` |

### 8.3 ILA: как снимать

- `reset_hw_ila`, `run_hw_ila -trigger_now`, `wait_on_hw_ila`,
  `upload_hw_ila_data`, `write_hw_ila_data -csv_file`.
- В ALWAYS-режиме триггер не работает — снимайте вручную в момент
  активности (например, в цикле прогонов).
- Смотрите не только `tvalid`, но и `tready`, `tlast`, `tdata`
  (меняются ли данные, идут ли `tlast` каждые 256).

### 8.4 Netlist-пробы (когда ILA в BD мало)

Скрипты `scripts/fsm_probe_impl.tcl`, `stuck_probe_impl.tcl`:

1. `open_run synth_1`;
2. `create_debug_core u_ila_0 ila`;
3. `create_debug_port` на каждую сеть (FSM state, tvalid, tready);
4. `opt/place/route/write_bitstream` + `write_debug_probes`.

Это позволяет увидеть состояние FSM, когда потоки «молчат».

### 8.5 Регистровые метки `dbg[]`

Дешёвый и мощный приём: ядро пишет в `dbg[i]` номера стадий
(`20+vy/128`, `30`, `40`, … `99`), счётчики, первые отсчёты. Хост
читает их после запуска. По меткам сразу видно, где ядро остановилось.
**Тонкость:** `dbg` может быть переставлен HLS-планировщиком; не
полагайтесь на порядок записи, смотрите значения.

### 8.6 Бисекция изменений

Оптимизации и «мелкие правки» ломают данные неочевидно. Метод:

1. Зафиксировать рабочую версию (git).
2. Вносить **одну** правку.
3. Проверять **тестом, чувствительным к этой правке**.
4. Если сломалось — откатить и проверить гипотезу отдельно.

Пример: раскладка strip и совмещение проходов были внесены вместе;
пришлось возвращать покадровые проходы, чтобы изолировать strip.

### 8.7 Тестовые изображения — какие и зачем

| Вход | Что ловит |
|:--|:--|
| константа | DC, масштаб, «нулевой AC» |
| горизонтальный градиент | отображение столбцов, фазу по X |
| вертикальный градиент | отображение строк, фазу по Y |
| пила/импульс | кадрирование FFT, перестановки |
| реальный кадр | полноценная проверка PSNR |

**Тонкость:** константа не проверяет AC. Если выход 128 на константе —
это ещё не значит, что ядро работает: проверяйте градиенты и пилу.

### 8.8 Соглашения, которые надо сверять с эталоном

- знак ДПФ (`e^{-i}` у xfft, у OpenCV — наоборот; отсюда conjugate LUT);
- центр плитки (`vx + hop/2`);
- порядок блоков и хвоста;
- Q-форматы и точку отсчёта.

Любое расхождение даёт «почти правильно»: корреляция 0.99, PSNR 27 дБ.

### 8.9 Залипшее состояние между запусками

Одна из самых неприятных категорий: **первый прогон после сброса
правильный, второй — нет**. Причина — данные, оставшиеся в AXIS-FIFO
или в конвейере xfft от предыдущего запуска. Ядро читает поток с
фиксированным числом отсчётов на кадр; лишний отсчёт сдвигает все
последующие кадры, и картинка «плывёт» (корреляция ~0.99, PSNR падает).

Как поймать:

- снять ILA в простое: если `inv_out`/`fwd_out` `tvalid=1` при
  `ap_idle`, в FIFO что-то осталось;
- прогнать ядро дважды подряд на одном входе и сравнить выходы;
- проверить, что число отправленных кадров равно числу принятых
  (счётчики/метки), и что последний `tlast` доходит до конца.

Лечение: не оставлять «хвостов» (точно считать кадры), при
необходимости — сбрасывать FFT/FIFO перед запуском (отдельный
host-управляемый reset в BD) или дренировать поток. В финальной
покадровой схеме этой проблемы нет; она всплыла в эксперименте с
совмещёнными send/recv.

### 8.10 Хроника реальной отладки (порядок, который стоит повторить)

1. **Ядро завершается, но выход весь 128.** Оказалось: вход
   `sample_t(y-128)/256` сатурировался, AC терялся. Симптом «плоское
   изображение» → проверять масштаб входа и `G`.
2. **Ядро виснет на первом проходе.** FSM-пробы показали ожидание
   `row_pass`. Причина — HLS dataflow с auto-rewind процессами
   (200-656). Лечение: убрать dataflow, сделать последовательные
   проходы.
3. **С внешними xfft ядро стоит, потоки молчат.** Минимальный тест
   «счётчик → xfft → ILA» доказал, что IP работает; значит, проблема
   в стыке/старте процессов.
4. **Loopback (без FFT) проходит все проходы.** Значит, арифметика и
   dataflow ядра живы; остаётся стык с xfft.
5. **После переписывания проходов ядро завершается, но в DDR нет
   данных.** `TKEEP/TSTRB=0` у AXIS-мастера → S2MM игнорирует beat.
6. **Выход 128 на реальном кадре.** Вход сатурировался (п.1). После
   исправления появился структурированный выход.
7. **Выход сдвинут на вектор движения.** Сравнение с CPU и сдвиг на
   +L показали сопряжённую фазу; инвертировали мнимую часть LUT.
8. **1080p: 27 дБ, 1024: 44 дБ.** Хвостовой блок не совпадал с CPU:
   CPU перекрывает 952–1023 хвостом, FPGA оставлял основной блок.
   Привели раскладку к CPU → 44.6 дБ.
9. **Ускорение.** Профиль → загрузка блока II=4 (32774 такта) →
   банки strip → II=1 (8198). Совмещение send/recv дало 53 мс, но
   сломало кадры xfft — откатили.

Вывод: почти каждый баг проявляется **конкретным тестовым сигналом**.
Держите набор тестов (константа, градиенты, пила, реальный кадр) и
прогоняйте его после каждой правки.

## 9. Тайминг и ускорение

### 9.1 Сначала профиль, потом оптимизация

Мы измерили: 96.5 мс ядро, 8.2 мс запись, 5.4 мс чтение.
Внутри ядра — оценки по тактам: загрузка блока 32k, row 16k,
col 27k, inv 18k, приём/выдача 23 мс. Оптимизировали самое дорогое.

### 9.2 II и банки памяти

- Смотрите отчёт HLS: `Final II`, latency, memory ports.
- Если II > 1 из-за памяти — раскладывайте массив по банкам.
- У нас `strip[32][8][W_MAX]` + `complete dim=2` дал II=1 и −18 мс.

### 9.3 Глубина FIFO и ширина потоков

- FIFO должны вмещать межкадровое расстояние (у нас 2048).
- Ширина 32 бита = 1 пиксель/такт; 1080p — 11.6 мс только на приём.
  128-битный поток даст 4 пикселя/такт (~3 мс) — следующий шаг.

### 9.4 Что дало сколько

| Изменение | Эффект |
|:--|:--|
| strip 8 банков (II=1) | 96.5 → 77.9 мс ядро |
| хвост по схеме CPU | +корректность 1080p (27.6 → 44.6 дБ) |
| FIFO 2048/2048 | помещается, BRAM 817/955 |
| совмещение send/recv | быстро (53 мс), но **некорректно** — откатили |

### 9.5 Почему не 60 fps

Остаток — 135 блоков × ~70k тактов + 23 мс на приём/выдачу.
Для 60 fps нужен конвейер блоков (processing нескольких плиток
одновременно) и 128-битный поток. Это отдельный этап.

## 10. Сборка, прошивка, воспроизводимость

### 10.1 HLS

```bash
cd hls/kernels/wiener_stream
vitis_hls -f build.tcl          # csynth + export в hw/ip_repo/wiener_stream
```

### 10.2 Vivado

```bash
# обновить IP в BD после экспорта
vivado -mode batch -source /tmp/upext.tcl   # upgrade_ip top_wiener_0_0
# полная сборка BD + synth + impl + bit
vivado -mode batch -source scripts/build_hw.tcl
```

`build_hw.tcl` пересобирает `top_synth_1` (BD OOC), затем `synth_1`,
`impl_1`, пишет `top_wrapper.bit` и проверяет WNS.

### 10.3 Два варианта битстрима из одного routed design

- **Cclk** — для флеша (по умолчанию);
- **JtagClk** — для JTAG-отладки:

```tcl
open_run impl_1
set_property BITSTREAM.STARTUP.STARTUPCLK JtagClk [current_design]
write_bitstream -force /tmp/top_wrapper_jtag.bit
```

Один и тот же place/route, меняется только startup clock — не нужно
пересобирать проект дважды.

### 10.4 MCS и флеш

```bash
vivado -mode batch -source scripts/make_mcs.tcl   # BPIX16, 64 МБ
vivado -mode batch -source scripts/flash.tcl      # erase/program/verify
```

**Тонкость:** после `boot_hw_device` startup может не завершиться
(особенность платы). Надёжен холодный старт. После JTAG/прошивки:

```bash
sudo scripts/reprobe.sh
```

### 10.5 Гигиена репозитория

- `.gitignore`: `hw/accel.runs/`, `hw/accel.gen/`, `hw/ip_repo/`,
  `hls/**/solution*`, `*.bit`, `*.mcs`, `clockInfo.txt`.
- BD-кэш `ipshared/*wiener_stream*` не коммитить (генерируется).
- Каждый этап — коммит с числами (ms, dB, WNS).

## 11. Чек-листы

### Перед синтезом

- [ ] HLS: все нужные циклы II=1 (или осознанно больше).
- [ ] Нет предупреждений 200-656 (dataflow) без понимания.
- [ ] `dbg`/регистры не раздувают интерфейс.
- [ ] Параметры/адреса совпадают с хостом.

### Перед запуском на железе

- [ ] `bar_probe` видит все устройства.
- [ ] `width/height/params` читаются.
- [ ] `out_scale` записан.
- [ ] DMA длины = размер кадра в байтах.
- [ ] Тайминг: WNS ≥ 0 (или осознанный минус).

### При отладке

- [ ] Сначала константа, потом градиенты, потом кадр.
- [ ] Проверить `dbg[]` — где остановилось.
- [ ] ILA: tvalid/tready/tlast/tdata.
- [ ] Прогнать дважды — нет ли залипшего состояния.
- [ ] Сравнить с CPU на **том же** входе и параметрах.

### При оптимизации

- [ ] Профиль до/после (не по ощущениям).
- [ ] Одна правка за раз.
- [ ] Проверка PSNR после каждой правки.
- [ ] Проверка хвоста/границ кадра.

## 13. Словарь

- **AXI-Stream** — потоковый интерфейс (tvalid/tready/tdata/tlast).
- **AXI-Lite** — регистровый интерфейс (mmap).
- **XDMA** — PCIe-движок Xilinx (хост↔DDR).
- **AXI DMA** — DMA DDR↔поток.
- **BD** — Block Design в Vivado IP Integrator.
- **HLS** — High-Level Synthesis (C++ → RTL).
- **II** — initiation interval, тактов между итерациями цикла.
- **WNS** — worst negative slack, запас по таймингу.
- **PSNR** — мера отличия изображений, дБ.
- **Q1.15 / Q1.23** — форматы фиксированной точки.
- **BPI** — параллельный NOR-флеш, отсюда загрузка платы.
